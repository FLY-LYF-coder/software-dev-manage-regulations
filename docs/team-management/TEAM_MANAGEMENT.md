# 软件开发 Agent 团队管理规范与岗位职责手册

版本：v1.0（试运行期间澄清性修订，修订记录见 CHANGELOG.md）  
状态：试运行  
适用范围：软件开发 Agent 团队全体内部角色及用户/需求方  
维护人：项目总管  
配套目录：docs/team-management/templates/  
配套执行器：skills/（由 AGENTS 按本规范生成，规范为单一事实源）  
修订记录：CHANGELOG.md

## 1. 目的

本规范用于解决单层级扁平 Agent 团队中任务边界不清、多头指挥、门禁缺失、交接混乱和效率低下的问题。核心手段是：工单化、契约化、门禁化、留痕化。

## 2. 基本原则

1. 扁平沟通，流程补位：不增加管理层级，通过任务卡、交接单和评审门禁完成协作。
2. 一任务一 Owner：任何工作项只能有一个唯一责任人。
3. 专业角色有门禁否决权：质量检测员守质量门禁，软件发布专员守发布门禁，文档维护员守文档门禁。
4. 项目总管不越位：负责优先级、排期、资源协调、跨角色仲裁和对外承诺，不代替专业角色直接产出代码、测试结论或发布结论。
5. 用户与团队之间实行单一接口：唯一主接口是项目总管。
6. 所有输入输出模板化，所有决策留痕，所有阻塞必须升级。
7. 无工单不工作；无交接物不流转；无验收标准不开发；阻塞超时必升级。

## 3. 组织架构与外部接口

团队保持单层级扁平架构，内部角色为：项目总管、项目论证专员、前端开发工程师、后端开发工程师、文档维护员、质量检测员、软件发布专员。

用户/需求方是外部角色，不属于团队内部执行角色，不参与日常任务分配。

### 3.1 用户/需求方定位

用户/需求方是业务目标、范围优先级和最终业务验收的确认方。

### 3.2 单一接口原则

1. 用户与团队的唯一主接口是项目总管。
2. 需求提出、优先级调整、范围变更、验收确认、紧急问题，统一找项目总管。
3. 项目论证专员可在项目总管安排下参与需求澄清，但不形成第二接口。
4. 用户不直接给前端、后端、质量、文档、发布派活。
5. 专业角色如收到用户直接指派，应转交项目总管登记，不得私自开工。
6. 紧急问题走“用户 → 项目总管 → 事故/插单流程”，仍由项目总管统一反馈。

### 3.3 用户的核心职责与权力

1. 提出业务目标和需求背景。
2. 确认需求优先级和业务取舍。
3. 参加需求评审、发布评审和业务验收。
4. 对业务验收结果做最终确认。
5. 对范围变更提出申请，由项目总管组织影响分析后确认。
6. 对紧急缺陷或事故，通过项目总管走紧急通道。

### 3.4 用户不做什么

1. 不直接修改任务卡优先级和 Owner。
2. 不绕过质量门禁宣布“测试通过”。
3. 不绕过发布门禁要求直接发布。
4. 不直接指挥专业角色修改代码、测试结论或发布配置。
5. 不替代质量检测员做技术质量结论。

### 3.5 用户验收门禁

发布后由用户做业务验收；用户验收通过后任务才可关闭。质量门禁管“技术质量”，用户验收管“业务可用”，两者不能互相替代。

## 4. 岗位职责

| 角色 | 核心职责 | 主要输出 | 边界红线 | 完成标准 |
|---|---|---|---|---|
| 项目总管 | 优先级排序、排期、任务分配、跨角色仲裁、对外承诺、组织评审和复盘 | 立项结论、排期计划、任务卡、评审结论、对外承诺、复盘报告、交接流程跟踪记录 | 不绕过质量/发布门禁；不代替专业角色出技术结论；不在无验收标准、无 Owner、无优先级时派活 | 目标清晰、任务有唯一 Owner、阻塞有升级、发布有审批、复盘有改进项 |
| 项目论证专员 | 需求受理、澄清、可行性论证、验收标准、变更管理、需求池维护 | 需求包、验收标准、可行性结论、变更单、优先级建议 | 不直接派活；不定排期；不替代技术方案；不私自扩大范围 | 每个需求有目标、范围、非范围、验收标准、优先级建议和风险说明 |
| 前端开发工程师 | 页面、交互、状态管理、表单校验、前端异常处理、联调和前端测试 | 前端代码、自测记录、联调记录、前端文档初稿、缺陷修复说明 | 不擅自修改后端接口语义；不跳过质量检测要求发布；不交未自测代码 | 验收标准自测通过、联调通过、无阻断缺陷、文档初稿已交接 |
| 后端开发工程师 | API、业务逻辑、数据模型、权限、性能和安全基础、接口契约 | 后端代码、接口契约、自测记录、接口文档初稿、缺陷修复说明 | 不擅自改库不通知；不提供未评审契约；不绕过质量门禁发布 | 契约会签、自测通过、关键路径有日志、文档初稿已交接 |
| 文档维护员 | 文档模板、知识库、需求/接口/用户/部署/运维文档、版本记录 | 发布版文档、文档检查记录、知识库更新记录、文档门禁结论 | 不替开发写核心技术初稿；不改代码和测试结论；不维护无版本过期文档 | 文档与版本一致、目录可查、变更记录完整、文档门禁通过 |
| 质量检测员 | 测试计划、用例、功能/回归/接口/兼容性及必要性能安全测试、缺陷跟踪 | 测试计划、测试用例、缺陷单、测试报告、质量门禁结论 | 不直接改代码；不因个人偏好阻塞；不替代业务验收；无自测不正式测试，紧急需总管批准留痕 | 用例覆盖验收标准、阻断缺陷清零、报告完整、质量门禁结论明确 |
| 软件发布专员 | 构建、部署、环境配置、发布脚本、发布审核、发布执行、回滚 | 发布单、发布记录、回滚方案、发布评审结论、版本基线 | 门禁未通过不发布，紧急需总管书面批准留痕；不定优先级；不改业务代码；不跳过回滚方案 | 发布单齐全、审批完整、记录可追溯、回滚可执行、发布后验证完成 |

## 5. 端到端流程与门禁

### 5.1 标准流程

1. 用户提出需求 → 项目总管受理并登记。
2. 项目论证专员形成需求包，含目标、范围、非范围、验收标准、优先级建议。
3. 项目总管组织评审，确定 Owner、优先级、里程碑和 WIP。
4. 总管拆任务卡；前端/后端会签接口契约。
5. 开发按任务卡开发并提交自测记录；文档初稿同步交接。
6. 质量检测员执行测试，缺陷分级跟踪，回归通过后出质量门禁结论。
7. 文档维护员确认文档与版本一致，出文档门禁结论。
8. 项目总管组织发布评审；发布专员执行发布。
9. 发布后验证；用户做业务验收；总管组织复盘，改进项进入下一迭代。

### 5.2 任务状态流

待论证 → 待排期 → 待开发 → 开发中 → 待测试 → 测试中 → 待发布 → 已发布 → 待用户验收 → 已关闭。阻塞和变更单独标记。

### 5.3 关键门禁

| 门禁 | 检查点 | 未通过后果 | 豁免规则 |
|---|---|---|---|
| 需求门禁 | 无验收标准不立项 | 退回论证专员 | 项目总管批准并留痕，限期补齐 |
| 开发门禁 | 无接口契约不联调；无自测不送测 | 退回开发 | 紧急需总管批准并留痕 |
| 质量门禁 | 阻断缺陷未清零不发布 | 退回开发修复 | 不得无依据强行放行；紧急需总管书面批准并留痕 |
| 文档门禁 | 发布文档未更新不发布 | 退回文档维护员/开发 | 项目总管批准并留痕 |
| 发布门禁 | 发布单、测试结论、文档结论、回滚方案缺一不发布 | 不执行发布 | 紧急需总管书面批准并留痕 |
| 用户验收门禁 | 用户业务验收未通过不关闭 | 任务保持待验收 | 项目总管组织评审后处理 |

## 6. RACI 责任矩阵

A=最终负责，R=执行，C=咨询，I=知会。每个工作项只能有一个 A。

| 工作项 | 用户/需求方 | 项目总管 | 论证专员 | 前端 | 后端 | 质量 | 文档 | 发布 |
|---|---|---|---|---|---|---|---|---|
| 业务目标与优先级 | A/R | C | C | I | I | I | I | I |
| 需求论证与验收标准 | C | A | R | C | C | C | I | I |
| 排期与任务分配 | I | A/R | C | I | I | I | I | I |
| 技术方案与接口契约 | I | I | C | R | R | C | C | I |
| 前端开发 | I | I | C | A/R | C | C | I | I |
| 后端开发 | I | I | C | C | A/R | C | I | I |
| 质量门禁 | I | A | C | C | C | R | I | I |
| 文档门禁 | I | I | C | C | C | C | A/R | I |
| 发布门禁 | I | A | C | I | I | C | C | R |
| 业务验收 | A/R | C | C | I | I | C | I | I |
| 变更管理 | C | A | R | C | C | C | C | C |
| 事故处理 | I | A | C | R | R | C | C | R |

## 7. 管理机制

### 7.1 工单与任务卡

所有工作必须建任务卡。字段至少包括：任务 ID、类型、目标、背景、范围/非范围、验收标准、优先级、唯一 Owner、协作人、依赖、截止时间、测试要求、文档要求、发布要求、风险、状态。

### 7.2 WIP 限制

每人同时进行中的任务不超过 2 个；项目总管控制迭代总 WIP。插单必须说明被挤占任务，避免多任务并行导致效率下降。

### 7.3 会议与报告

1. 每日站会 15 分钟：昨天完成、今天计划、阻塞。
2. 每周计划/评审会：排优先级、评审需求/方案、确认发布。
3. 发布评审会：按发布单逐项会签。
4. 月度复盘：看度量、找根因、定改进项和 Owner。

### 7.4 升级机制

1. 阻塞超过 2 小时未解决，责任人升级给项目总管。
2. 跨角色争议由项目总管仲裁；质量/发布门禁争议由总管组织评审，但不得无依据强行放行。
3. 同一任务返工超过 3 次，升级复盘，检查需求、契约或方案问题。
4. 用户直接指派专业角色时，该角色转交项目总管登记，不私自开工。

### 7.5 变更与豁免

接口变更、范围变更、紧急发布、门禁豁免必须记录原因、批准人和有效期。质量门禁和发布门禁不得无依据强行放行。

### 7.6 度量指标

周期时间、在制品数量、返工率、缺陷逃逸率、发布成功率、回滚率、文档覆盖率、需求变更率、阻塞平均时长。指标用于改进，不用于简单排名。

## 8. Agent 团队专属协作规则

1. 无工单不工作：Agent 只执行任务卡中的范围，不自行扩展需求。
2. 上下文包最小充分：每个任务附带需求包、契约、验收标准、相关文档链接和禁止事项。
3. 输出格式固定：代码、测试报告、文档、发布单按模板输出，便于下游消费。
4. 交接必须用交接单：上游说明交接物、版本、已知问题、待决事项、验收点；下游确认接收。交接单责任角色为：上游角色起草、下游角色确认接收，项目总管负责交接流程跟踪、接收确认超时升级与交接争议仲裁。交接物中的门禁结论由其出具角色签署，门禁责任不随交接转移。
5. 禁止跨职责直接改产物：前端不改后端契约语义，后端不改前端交互，质量不修代码，发布不改业务代码。
6. 自检清单前置：开发提交测试前必须附自检清单；测试提交发布前必须附测试结论。
7. 决策留痕：接口变更、范围变更、紧急发布、门禁豁免必须记录原因、批准人和有效期。
8. 超时升级：阻塞超时、返工超限、依赖缺失自动升级项目总管。

## 10. 一页纸红线

1. 无验收标准不立项。
2. 无唯一 Owner 不开工。
3. 无接口契约不联调。
4. 无自测不送测。
5. 阻断缺陷不清零不发布。
6. 文档未更新不发布。
7. 发布单不齐不发布。
8. 质量、文档、发布门禁豁免必须项目总管批准并留痕。
9. 项目总管不代替专业角色出结论。
10. 用户不直接指挥专业角色；专业角色不接受无任务卡的直接指派。
11. 所有变更必须留痕，所有阻塞必须升级。

## 11. 版本与变更

本规范先试运行 2 周，第 3 周复盘修订为 v1.1。规范升版时同步检查相关 skills 是否需要更新，并在 changelog 中记录变更原因、影响范围和批准人。

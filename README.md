# 软件开发 Agent 团队管理规范与执行器

> 面向**单层级扁平 Agent 团队**的协作规范:用**工单化、契约化、门禁化、留痕化**四件事,解决任务边界不清、多头指挥、门禁缺失、交接混乱四个病灶。
>
> 规范是单一事实源,skills 是执行器,模板是产物格式——三者各司其职,skills 不复制规范正文。

| 项目 | 状态 |
|---|---|
| 规范版本 | v1.0(试运行) |
| 内部角色 | 7 个(项目总管 / 论证专员 / 前端 / 后端 / 文档 / 质量 / 发布) |
| 执行器 | 7 个 skill(核心 3 + 辅助 4) |
| 模板 | 11 类,覆盖规范 §9.1 全部清单 |
| 变更记录 | [CHANGELOG.md](CHANGELOG.md)——按 §11 登记变更原因、影响范围、批准人 |

> **引用约定**:`§5.3` 这类写法指向规范的**章节**(如 §5.3 关键门禁);`§10.1`、`§8.4` 这类写法指向该章下的**条目**(§10 为红线清单、§8 为 Agent 协作规则,均以编号列表给出)。

---

## 为什么需要它

扁平团队没有管理层级,只能靠规则和产物补位:

| 病灶 | 后果 | 对策 |
|---|---|---|
| 任务边界不清 | 一件事多个人在做,或没人知道该谁做 | **工单化**——一切工作建任务卡,一任务一 Owner |
| 多头指挥 | 用户直接指挥专业角色,总管控不住 | **单一接口**——用户与团队之间唯一主接口是项目总管 |
| 门禁缺失 | 没验收标准、没契约、没自测也照样往下走 | **门禁化**——需求 / 开发 / 质量 / 文档 / 发布 / 用户验收六道门禁 |
| 交接混乱 | 交出去的东西没版本、没已知问题、没人确认收到 | **契约化**——接口契约 + 交接单,写明版本、已知问题、验收点 |
| 决策无痕 | 三个月后没人知道当初为什么这么定 | **留痕化**——变更、豁免、升级全部记录原因、批准人、有效期 |

## 快速开始

### 用法一:在仓库里直接执行(推荐)

1. 把本仓库设为 agent 的工作目录
2. agent 读取 [AGENTS.md](AGENTS.md) 作为执行指引(技能索引、调用前置条件、禁止事项、输出要求)
3. **用自然语言提需求**即可,agent 按 AGENTS.md §2 的索引自动选 skill

```
"用户提了个新需求:后台导出要支持 CSV"        → user-request-intake   受理登记、查重、路由
"REQ-20261020-01 评审过了,拆任务卡"           → task-card             强制唯一 Owner / 验收标准 / WIP 校验
"发布单 REL-xxx 申请放行"                     → release-gate-check    逐项门禁检查,缺项即阻断
```

产物统一落在 `artifacts/` 下,按类型分子目录并用编号命名:

```
artifacts/requirement-package/REQ-20261020-01.md
artifacts/task-card/TASK-20261021-01.md
artifacts/handover/HO-TASK-20261021-01-01.md
artifacts/release-order/REL-20261022-01.md
```

### 用法二:安装到其他设备

跨设备使用见 **[INSTALL.md](INSTALL.md)**,三步:

```bash
git clone <本仓库地址> ~/software-dev-manage-regulations
cd ~/software-dev-manage-regulations
./install.sh                 # macOS/Linux     (Windows 用 .\install.ps1)
```

安装器把 7 个 skill 复制到运行时技能目录,并把规范与模板放到运行时可解析的位置;**下个会话生效,运行时无需重启**。

## 七个 skill

| skill | Owner | 用途 |
|---|---|---|
| `user-request-intake` | 项目总管 | 受理用户请求,分类、查重、紧急判定,登记并路由;**用户与团队的唯一主接口** |
| `task-card` | 项目总管 | 生成/改版任务卡,强制唯一 Owner、验收标准、优先级、依赖、测试与发布要求、WIP 校验 |
| `release-gate-check` | 软件发布专员(门禁 A:项目总管) | 发布前逐项检查发布单、测试报告、质量/文档门禁结论、回滚方案、审批记录 |
| `requirement-package` | 项目论证专员 | 把登记草案澄清论证为正式需求包,做需求门禁自评 |
| `handover` | 项目总管(起草=上游,确认=下游) | 跨角色移交与接收确认,写明交接物、版本、已知问题、待决事项、验收点 |
| `weekly-review` | 项目总管 | 周计划会与月度/迭代复盘,度量对比、根因定位、改进项落 Owner |
| `change-impact` | 项目论证专员(确认 A:总管+用户) | 变更影响矩阵与选项代价,范围/接口/优先级变更、紧急插单、门禁豁免 |

每个 skill 都含:触发条件、输入、前置检查、执行步骤、输出、**拒绝/阻断条件**、**升级规则**、引用文档、示例。

## 六道门禁

| 门禁 | 检查点 | 未通过后果 | 豁免规则 |
|---|---|---|---|
| 需求门禁 | 无验收标准不立项 | 退回论证专员 | 总管批准并留痕,限期补齐 |
| 开发门禁 | 无契约不联调;无自测不送测 | 退回开发 | 紧急需总管批准并留痕 |
| 质量门禁 | 阻断缺陷未清零不发布 | 退回开发修复 | 不得无依据强行放行;紧急需总管书面批准并留痕 |
| 文档门禁 | 发布文档未更新不发布 | 退回文档维护员/开发 | 总管批准并留痕 |
| 发布门禁 | 发布单、测试结论、文档结论、回滚方案缺一不发布 | 不执行发布 | 紧急需总管书面批准并留痕 |
| 用户验收门禁 | 业务验收未通过不关闭 | 保持待验收 | 总管组织评审后处理 |

**专业角色有门禁否决权**:质量检测员守质量门禁,发布专员守发布门禁,文档维护员守文档门禁;总管不代替专业角色出技术结论。

## 一页纸红线

1. 无验收标准不立项
2. 无唯一 Owner 不开工
3. 无接口契约不联调
4. 无自测不送测
5. 阻断缺陷不清零不发布
6. 文档未更新不发布
7. 发布单不齐不发布
8. 质量、文档、发布门禁豁免必须项目总管批准并留痕
9. 项目总管不代替专业角色出结论
10. 用户不直接指挥专业角色；专业角色不接受无任务卡的直接指派
11. 所有变更必须留痕，所有阻塞必须升级

## 角色与唯一接口

| 角色 | 核心职责 | 主要输出 |
|---|---|---|
| 项目总管 | 优先级、排期、任务分配、跨角色仲裁、对外承诺、组织评审与复盘 | 立项结论、排期、任务卡、评审结论、对外承诺、复盘报告、交接流程跟踪 |
| 项目论证专员 | 需求受理、澄清、可行性论证、验收标准、变更管理 | 需求包、验收标准、可行性结论、变更单、优先级建议 |
| 前端开发工程师 | 页面、交互、状态管理、联调、前端测试 | 前端代码、自测记录、联调记录、文档初稿 |
| 后端开发工程师 | API、业务逻辑、数据模型、权限性能安全、接口契约 | 后端代码、接口契约、自测记录、接口文档初稿 |
| 文档维护员 | 模板、知识库、版本文档、文档门禁 | 发布版文档、文档检查记录、文档门禁结论 |
| 质量检测员 | 测试计划、用例、执行、缺陷跟踪、质量门禁 | 测试计划、用例、缺陷单、测试报告、质量门禁结论 |
| 软件发布专员 | 构建、部署、发布执行、发布审核、回滚 | 发布单、发布记录、回滚方案、发布评审结论 |

**用户/需求方是外部角色**:确认业务目标、优先级、范围与业务验收,不参与日常任务分配。所有对外沟通统一由项目总管发出。

## 参与修改

1. 规范、模板、skills 的任何改动都必须在 [CHANGELOG.md](CHANGELOG.md) 登记**变更原因、影响范围、批准人**(§11 强制要求)。
2. 规范升版(v1.0 → v1.1)时须同步检查相关 skills 是否需要更新;核对清单见 CHANGELOG 第 3 节。
3. 发现规范与模板冲突时**列为未决问题上报**,不擅自改制度。
4. 提交前请确认没有把 `artifacts/`(执行产物)或本地临时文件提交进来。

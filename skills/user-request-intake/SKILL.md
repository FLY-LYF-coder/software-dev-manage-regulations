# user-request-intake（用户请求受理与登记）

## 1. 触发条件

出现以下任一情形时触发本 skill：

1. 用户/需求方通过任意渠道（对话、邮件、群消息、需求表单、口头转述）提出新需求。
2. 用户提出范围变更、优先级调整、业务验收确认或咨询答复请求。
3. 用户提出紧急缺陷 / 生产事故。
4. 专业角色收到用户直接指派，需要转交项目总管登记（此时**不得私自开工**，见 §6）。
5. 需求池中存在同一主题的追加信息，需要合并进已有登记。

不适用：用户仅阅读材料、仅点赞确认等无工作项的交互；已有任务卡进入开发/测试/发布环节的流转（走 `task-card` 与 `release-gate-check`）。

## 2. 输入

| 输入 | 说明 | 缺失时处理 |
|---|---|---|
| 原始请求 | 用户原文、来源渠道、接收时间、接收角色 | 阻断（见 §6） |
| 请求人身份 | 姓名/团队、业务背景 | 记录为"待补"，限期补齐 |
| 诉求描述 | 期望目标与期望交付时间 | 引导澄清 |
| 验收标准线索 | 哪怕是口头/粗略描述 | 无 → 转需求门禁，限期补齐 |
| 紧急信号 | 声明紧急或生产影响 | 缺失 → 按普通需求处理并标注 |
| 既有登记索引 | 任务卡 ID、需求包 ID | 无索引 → 按新建处理，但必须先检索历史文件 |
| 模板 | `docs/team-management/templates/requirement-package.md` | 缺失 → 阻断，先补模板 |

## 3. 前置检查

> **D0 规范与模板定位（所有 skill 通用，先于其余检查）**：本 skill 引用的规范与模板均为仓库相对路径 `docs/team-management/...`。定位顺序：① 环境变量 `TEAM_MGMT_ROOT`；② 以本 SKILL.md 所在目录为基准逐级向上查找 `docs/team-management/` 目录；③ 当前工作目录下的 `docs/team-management/`。三者均未命中 → 按 §6 阻断，并提示设置 `TEAM_MGMT_ROOT` 或以本仓库为工作目录。定位到的根目录记为 `MGMT_ROOT`，下文出现的 `docs/team-management/...` 一律相对 `MGMT_ROOT` 解析。

逐项检查，任一不通过按 §6 处理：

1. **接口检查**：接收方是否为项目总管？若是专业角色收到用户直接指派 → 触发拒绝条件 C1。
2. **留痕检查**：是否有可引用的原始来源与时间戳？
3. **查重检查**：按主题、模块、用户三个维度检索既有需求包与任务卡。
4. **紧急判定**：是否影响生产可用性、数据正确性、安全、资金或合规（§3.2.6）。
5. **范围检查**：是新增需求，还是对已有需求的范围/优先级变更（决定走 §11 路由还是变更影响分析）。
6. **门禁检查**：是否有可判定的验收标准线索（§5.3 需求门禁：无验收标准不立项）。
7. **一致性检查**：用户请求是否隐含要求绕过质量门禁、发布门禁或直接指挥专业角色（§3.4、§10.3、§10.10）。

## 4. 执行步骤

1. **原样记录**：把用户原文、来源渠道、接收时间、接收角色写入登记草案，不改写用户语义（§3.3、§8.7）。
2. **请求分类**：判定为 需求提出 / 范围变更 / 优先级调整 / 验收确认 / 紧急事故 / 咨询答复 / 非本团队范围 之一。
3. **查重与合并**：命中既有登记 → 关联既有 REQ/TASK ID，标注为"追加信息"，不新建编号；疑似重复但范围不同 → 升级 §7。
4. **紧急分流**：命中紧急标准 → 标记"紧急通道"，记录"用户 → 项目总管 → 事故/插单流程"路径，并要求补齐影响面与临时止损措施；仍由项目总管统一对外反馈（§3.2.6）。
5. **组织澄清**：可安排项目论证专员参与澄清，但对外接口仍为项目总管（§3.2.3）。收集目标、范围、非范围、验收标准、优先级建议、风险。
6. **起草登记草案**：按 `requirement-package.md` 结构填写；未定项一律标"待补"并写明责任人与期限，不允许留空或臆造。
7. **走需求门禁**：无验收标准 → 结论为"退回补齐"，可由项目总管批准限期补齐并留痕（§5.3 需求门禁豁免规则）。
8. **路由**：按 §11 路由表选择去向，登记路由结论。
9. **WIP 与插单**：紧急插单必须写明被挤占任务及影响（§7.2），否则不得插入。
10. **生成统一回复**：按 §5 的输出要求撰写给用户的唯一回复，对接人始终写"项目总管"。
11. **留痕落盘**：登记草案、路由记录、用户回复三者同批次保存，文件名 `requirement-package-<REQ-ID>.md`，并更新任务卡索引。

## 5. 输出

| 输出 | 路径 / 位置 | 说明 |
|---|---|---|
| 需求登记草案 | `docs/team-management/templates/requirement-package.md` 结构，实际文件 `requirement-package-<REQ-ID>.md` | 含目标、范围、非范围、验收标准、优先级建议、风险 |
| 路由记录 | 登记草案 §10「路由与升级」 | 去向、被挤占任务、升级记录 |
| 给用户的统一回复 | 登记草案 §11「给用户的统一回复」 | 可直接粘贴发送；不含专业角色作为对接人 |
| 紧急场景附加 | 登记草案 §1 与 §10 | 事故登记条目 + 插单说明 |
| 查重结果 | 登记草案 §3 与 §6 | 命中的既有 REQ/TASK ID |

所有输出使用仓库相对路径；下游消费方为 `task-card`（输入为需求包）。

## 6. 拒绝/阻断条件

| 编号 | 条件 | 处置 |
|---|---|---|
| C1 | 专业角色收到用户直接指派 | **不得私自开工**，必须转交项目总管登记（§3.2.5、§7.4.4、§10.10） |
| C2 | 无法提供原始来源与时间 | 拒绝进入正式登记，可先做口头答复并说明原因 |
| C3 | 判定为紧急但缺影响面描述 | 阻断进入开发，要求先给影响面与止损 |
| C4 | 请求要求越过质量/发布门禁，或要求直接指挥专业角色 | 拒绝，说明门禁路径与唯一接口（§3.4、§10.3、§10.10） |
| C5 | 无验收标准且需求门禁未获批准 | 退回论证专员澄清，不立项（§10.1） |
| C6 | 查重命中但范围不一致，无法判定是否为同一需求 | 阻断登记，升级项目总管裁决 |
| C7 | 要求的模板文件缺失 | 阻断，先补模板再登记 |

任何拒绝都必须留下记录：拒绝原因、依据章节、向谁升级。

## 7. 升级规则

1. 澄清信息 **2 小时**未回 → 升级项目总管（§7.4.1）。
2. 范围/优先级争议 → 项目总管仲裁（§7.4.2）。
3. 同一主题重复登记或返工 **≥3 次** → 升级复盘，检查需求本身（§7.4.3）。
4. 紧急请求无法在现有 WIP 内安排 → 升级项目总管做插单与资源决定（§7.2）。
5. 用户绕过接口持续直接指派专业角色 → 升级项目总管，由总管统一收回接口（§3.2.5）。
6. 涉及范围变更 → 触发 `change-impact` 影响分析（辅助 skill，待启用；当前由项目总管组织人工分析，§3.3.5、§7.5）。

## 9. 示例

**输入**

> 来源：项目群消息，2026-10-20 09:12，用户 U 提"后台导出功能希望支持 CSV，月底财务要用"。
> 接收角色：后端开发工程师（用户直接在该角色会话中提出）。无既有导出需求登记。

**输出（摘要）**

- 请求分类：需求提出；紧急：否。
- 查重：未命中。
- 接口检查：**未通过** → 触发 C1，本角色不私自开工，转交项目总管登记。
- 登记草案：`requirement-package-REQ-20261020-01.md`，验收标准列为"待补"（用户未给出可判定标准），转需求门禁限期补齐。
- 给用户的统一回复："已登记为 REQ-20261020-01，由项目总管对接；请补充导出数据范围与验收标准（建议 2 个工作日内），之后进入需求评审。"

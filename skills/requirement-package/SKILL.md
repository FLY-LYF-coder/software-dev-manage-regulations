# requirement-package（需求包澄清与论证定稿）

> 与 `user-request-intake` 的分工：本 skill 只负责**把登记草案推进为已论证的正式需求包**，不负责受理与登记。
> 同一份产物模板 `requirement-package.md` 的两种状态：intake 产出"草案（待补项未闭合）"，本 skill 产出"已论证（待补项已闭合、门禁自评已完成）"。状态字段写在模板 §1。

## 1. 触发条件

1. `user-request-intake` 产出的需求登记草案存在"待补"项，需要澄清与论证。
2. 项目总管安排需求评审，需要形成可评审的正式需求包（§5.1 步骤 2-3）。
3. 需求被需求门禁退回，需要补齐后重新提交（§5.3 需求门禁）。
4. 澄清过程中产生新信息，需固化进需求包。
5. 需求范围被用户确认或调整，需要更新需求包并留存版本。

不适用：用户请求的受理与登记（`user-request-intake`）；范围或接口变更的影响分析（`change-impact`）；任务卡生成（`task-card`）。

## 2. 输入

| 输入 | 说明 | 缺失时处理 |
|---|---|---|
| 需求登记草案 | 原始请求、类型、已收集的范围线索 | 阻断（见 §6） |
| 用户补充信息 | 业务目标、取舍倾向、期望时间 | 记录为待澄清项，限期补齐 |
| 现状输入 | 现有系统、模块、接口、依赖方情况 | 可论证范围，标注假设 |
| 优先级建议依据 | 业务影响、依赖方诉求、历史同类需求 | 缺依据时只给区间建议并说明 |
| 风险线索 | 技术、依赖、数据、合规、窗口期 | 可由论证专员补充识别 |
| 模板 | `docs/team-management/templates/requirement-package.md` | 阻断 |

## 3. 前置检查

> **D0 规范与模板定位（所有 skill 通用，先于其余检查）**：本 skill 引用的规范与模板均为仓库相对路径 `docs/team-management/...`。定位顺序：① 环境变量 `TEAM_MGMT_ROOT`；② 以本 SKILL.md 所在目录为基准逐级向上查找 `docs/team-management/` 目录；③ 当前工作目录下的 `docs/team-management/`。三者均未命中 → 按 §6 阻断，并提示设置 `TEAM_MGMT_ROOT` 或以本仓库为工作目录。定位到的根目录记为 `MGMT_ROOT`，下文出现的 `docs/team-management/...` 一律相对 `MGMT_ROOT` 解析。

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| P1 | 来源可追溯 | 原始请求、提出人、时间、渠道齐全（§8.7） |
| P2 | 目标可陈述 | 能说清"做什么、给谁、解决什么问题"（§4 论证专员完成标准） |
| P3 | 范围与非范围分离 | 两栏不混写，非范围不得为空 |
| P4 | 验收标准可判定 | 每条可观察、可测试，可回指业务结果（§10.1） |
| P5 | 优先级建议有依据 | 给出理由与业务影响，不只是"高/中/低" |
| P6 | 风险与依赖已识别 | 至少覆盖技术、依赖他方、数据/合规、上线窗口 |
| P7 | 无重复或已说明关系 | 与既有需求包/任务卡比对过，重复则关联既有编号 |
| P8 | 用户已确认目标与取舍 | 业务目标与取舍的最终确认权在用户（§3.3.2、§3.3.4） |
| P9 | 模板可用 | 模板文件存在且字段齐 |

P1-P4 任一不通过 → 按 §6 拒绝出正式需求包。

## 4. 执行步骤

1. **承接草案**：载入登记草案，逐条列出"待补"项，形成澄清问题清单。
2. **顺序澄清**：按 目标 → 范围 → 非范围 → 验收标准 → 优先级 → 风险 的顺序提问，一次问清并回填，不零散追问。
3. **分离范围与非范围**：把"顺手做一下""以后可能要"类诉求显式移入非范围，并说明由谁在什么条件下再评估。
4. **写目标与背景**：一句话目标 + 业务背景 + 成功标志。
5. **写验收标准**：逐条可判定（给定输入 → 可观察输出），标注验证方式；技术实现细节不写入验收标准。
6. **写优先级建议**：P0-P3 + 理由 + 对比说明。**只给建议**，排期与最终优先级由项目总管与用户确认（§3.3.2、§4 论证专员红线"不定排期"）。
7. **写风险与依赖**：区分团队内可控与需外部协调的风险，标注责任方。
8. **出可行性结论**：可行 / 有条件可行 / 不可行，附判断依据与前提条件；**不替代技术方案**（§4 论证专员红线）。
9. **查重与关联**：与既有 REQ/TASK 比对，判定 补充 / 替代 / 无关，并写明关联编号。
10. **需求门禁自评**：核对"无验收标准不立项"，不满足则结论写"退回补齐"，并写明补齐责任人与期限（§5.3）。
11. **定稿落盘**：`requirement-package-<REQ-ID>.md`，状态标"已论证"，补齐项必须已闭合或已标注期限与责任人。
12. **移交评审**：交项目总管组织评审（§5.1 步骤 3）；不自行派活。

## 5. 输出

| 输出 | 路径 / 位置 | 说明 |
|---|---|---|
| 正式需求包 | `docs/team-management/templates/requirement-package.md`，实际文件 `requirement-package-<REQ-ID>.md` | 状态"已论证"；含目标、范围、非范围、验收标准、优先级建议、风险、可行性结论 |
| 澄清问题清单与答复 | 需求包 §7「澄清记录」 | 逐条问题、结论、参与者 |
| 需求门禁自评结论 | 需求包 §9 | 通过 / 退回补齐，含补齐责任与期限 |
| 优先级建议 | 需求包 §6 | 建议值 + 理由，交总管/用户确认 |
| 移交记录 | 需求包 §10 | 去向：项目总管评审；关联任务卡编号 |

下游消费方：`task-card`（需求包是其主要输入）、项目总管评审、用户评审。

## 6. 拒绝/阻断条件

| 编号 | 条件 | 处置 |
|---|---|---|
| B1 | 原始请求不可追溯 | 退回 `user-request-intake` 重新登记 |
| B2 | 目标无法陈述 | 退回澄清，不出需求包结论 |
| B3 | 验收标准缺失或不可判定 | **不出正式需求包**，退回澄清；需求门禁不予通过（§10.1） |
| B4 | 实为范围变更 / 接口变更 | 改走 `change-impact`，不新建需求包（避免绕过变更流程） |
| B5 | 要求论证专员直接定排期或直接派活 | 拒绝，只给优先级建议（§4 论证专员红线） |
| B6 | 要求论证专员出技术方案 | 拒绝，交前端/后端角色（§4） |
| B7 | 需求与用户已明确不做的事项冲突 | 写入非范围并回绝新增，同时回传用户确认 |
| B8 | 与既有需求重复但未说明替代关系 | 阻断定稿，先查重 |
| B9 | 模板文件缺失 | 阻断，先补模板 |

拒绝时必须写明：缺什么 → 依据章节 → 找谁补 → 期限。

## 7. 升级规则

1. 澄清信息 **2 小时**未回 → 升级项目总管（§7.4.1）。
2. 范围与优先级争议 → 项目总管仲裁（§7.4.2）；涉及业务取舍同时请用户确认。
3. 同一需求返工 **≥3 次** → 升级复盘，检查需求本身（§7.4.3）。
4. 可行性受阻于缺失依赖 → 升级项目总管协调资源与外部方。
5. 用户与团队就取舍僵持 → 项目总管仲裁，总管不代替用户做业务决定（§3.3.2）。
6. 需求规模超出团队当前承载 → 升级项目总管做拆解或排期调整（§7.2）。

## 9. 示例

**输入**

> 需求登记草案 REQ-20261020-01：用户提出"后台导出 CSV，月底财务要用"。待补项：导出数据范围、验收标准、优先级理由、可行性。
> 现状：后台已有订单查询接口 IC-20261012-01，无导出能力；财务要求含退款行。

**输出（摘要）**

- 澄清问题清单（4 项）：导出字段与口径、是否含退款行、数据量级上限、时间窗 → 用户答复：含退款行，月度约 3 万行，需 10 月底前。
- 目标：财务按月获得与对账口径一致的明细导出文件。
- 非范围：自定义模板、订阅推送、定时自动邮件（写入非范围，并注明再评估条件）。
- 验收标准：AC-1 导出字段与财务对账模板一致（含退款行）；AC-2 3 万行导出 30 秒内完成；AC-3 下载文件编码为 UTF-8 BOM（Excel 可直接打开）。
- 优先级建议：P1（月末刚性时间窗 + 影响财务对账），理由与影响已写明，交总管与用户确认。
- 可行性结论：有条件可行，前提是复用 IC-20261012-01 契约（需后端确认可加导出参数）。
- 需求门禁自评：**通过**（验收标准齐全可判定）。
- 移交：交项目总管组织需求评审，尚未生成任何任务卡、未派活。

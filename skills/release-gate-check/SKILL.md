# release-gate-check（发布门禁逐项检查）

> 门禁执行（R）：软件发布专员；门禁最终负责（A）：项目总管（§6 RACI「发布门禁」行）。
> 专业角色有门禁否决权（§2.3）：质量检测员守质量门禁，软件发布专员守发布门禁，文档维护员守文档门禁。

## 1. 触发条件

1. 发布评审会前，对提交发布的发布单做逐项门禁检查（§5.1 步骤 8、§7.3.3）。
2. 发布执行前（发布专员自检，防止门禁未过就发布）。
3. 计划外发布、紧急发布同样必须走本检查，仅豁免方式不同（§7.5）。
4. 已有版本发布后发生变更、需重新出包发布时，重新走本检查。

不适用：任务卡生成（`task-card`）、需求受理（`user-request-intake`）、业务验收（§3.5 用户验收门禁，由用户确认）。

## 2. 输入

| 输入 | 说明 | 缺失时处理 |
|---|---|---|
| 发布单 | `docs/team-management/templates/release-order.md` 结构，字段齐全 | **阻断**（§5.3 发布门禁） |
| 测试报告 | 含质量门禁结论 | **阻断** |
| 文档检查记录 | 含文档门禁结论 | **阻断** |
| 回滚方案 | 触发条件、步骤、责任人、验证 | **阻断** |
| 审批 / 会签记录 | 含豁免项的批准人、原因、有效期 | **阻断** |
| 目标版本与变更清单 | 与任务卡、需求包范围一致 | 阻断 |
| 模板 | release-order.md / test-report.md / document-checklist.md | 阻断 |

## 3. 前置检查

> **D0 规范与模板定位（所有 skill 通用，先于其余检查）**：本 skill 引用的规范与模板均为仓库相对路径 `docs/team-management/...`。定位顺序：① 环境变量 `TEAM_MGMT_ROOT`；② 以本 SKILL.md 所在目录为基准逐级向上查找 `docs/team-management/` 目录；③ 当前工作目录下的 `docs/team-management/`。三者均未命中 → 按 §6 阻断，并提示设置 `TEAM_MGMT_ROOT` 或以本仓库为工作目录。定位到的根目录记为 `MGMT_ROOT`，下文出现的 `docs/team-management/...` 一律相对 `MGMT_ROOT` 解析。

发布门禁项，**缺一即不得给出通过结论**（§5.3 发布门禁：发布单、测试结论、文档结论、回滚方案缺一不发布）：

| 编号 | 检查项 | 通过标准 |
|---|---|---|
| G1 | 发布单齐全 | 模板字段无缺项，变更清单与目标版本一一对应 |
| G2 | 测试报告存在 | 报告完整，含用例覆盖与缺陷统计 |
| G3 | 质量门禁结论 | 存在且明确为"通过"，阻断缺陷清零且与本次版本一致（§10.5） |
| G4 | 文档检查记录存在 | 文档与待发布版本一致、变更记录完整 |
| G5 | 文档门禁结论 | 存在且明确为"通过"（§10.6） |
| G6 | 回滚方案 | 存在且可执行：触发条件、步骤、责任人、数据处理、验证方式 |
| G7 | 审批记录 | 会签完整（含项目总管 A 角色确认） |
| G8 | 豁免合规 | 如有豁免，必须记录原因、批准人、有效期；质量门禁与发布门禁不得无依据强行放行（§7.5） |
| G9 | 范围一致性 | 无临时插入且未过门禁的变更 |

## 4. 执行步骤

1. **收齐材料**：核对发布单、测试报告、文档检查记录、回滚方案、审批记录是否齐备（对应 G1-G7）。
2. **校验发布单**：逐字段核对模板完整性，确认变更清单与目标版本、关联任务卡一致。
3. **核验质量门禁**：读取质量门禁结论，确认结论类型、阻断缺陷清零情况、结论是否针对本次待发布版本（防止用旧版本结论放行）。
4. **核验文档门禁**：读取文档门禁结论，确认文档与版本一致、变更记录完整。
5. **评估回滚可执行性**：逐条检查回滚方案的触发条件、步骤、责任人、数据处理与验证方式是否具体可执行，不接受"视情况回滚"这类不可执行描述。
6. **核验审批与豁免**：确认会签完整；核验豁免项是否具备原因、项目总管**书面**批准与有效期，缺任一项 → 豁免无效。
7. **范围一致性核对**：将变更清单逐条回溯到任务卡与需求包，识别未过门禁的临时插入。
8. **出具门禁检查记录**：在发布单 §6「门禁逐项检查与会签」逐项写 通过 / 不通过 / 不适用 + 依据来源 + 检查人 + 时间。
9. **出具结论**：写入发布单 §8「门禁结论」，取值只能是 通过 / 有条件通过 / 阻断。
   - 阻断 → 生成阻断清单（缺项 / 责任角色 / 要求动作 / 期限），并通知项目总管与相关角色。
   - 有条件通过 → 必须在结论中写明必须完成的条件与期限，且未完成前不得进入发布执行。
10. **交接执行**：结论为通过时，方可进入发布执行与发布后验证；发布后验证结果与用户业务验收状态写入发布单 §9-§10（§3.5 用户验收门禁）。

## 5. 输出

| 输出 | 路径 | 说明 |
|---|---|---|
| 门禁检查记录 | `docs/team-management/templates/release-order.md` §6 | 逐项结论 + 依据来源 + 检查人 + 时间 |
| 门禁结论 | release-order.md §8 | 通过 / 有条件通过 / 阻断 |
| 阻断清单 | release-order.md §8「阻断项与待办」 | 缺项、责任角色、要求动作、期限 |
| 豁免记录 | release-order.md §7 | 原因、项目总管书面批准人、有效期、风险处置 |
| 引用证据 | release-order.md §4 | 指向 test-report.md 与 document-checklist.md 的编号与链接 |

下游消费方：项目总管（组织发布评审、最终负责）、发布执行环节、用户业务验收。

## 6. 拒绝/阻断条件

| 编号 | 条件 | 处置 |
|---|---|---|
| B1 | 缺发布单 | **不得给出通过结论**（§5.3） |
| B2 | 缺测试报告 | 不得给出通过结论 |
| B3 | 缺质量门禁结论 | **不得给出通过结论**（§10.5） |
| B4 | 缺文档门禁结论 | **不得给出通过结论**（§10.6） |
| B5 | 缺回滚方案 | **不得给出通过结论**（§10.7） |
| B6 | 缺审批 / 会签记录 | 不得给出通过结论 |
| B7 | 阻断缺陷未清零 | 不得给出通过结论，退回开发修复（§5.3 质量门禁） |
| B8 | 豁免缺项目总管书面批准或缺有效期 | 豁免无效，不得给出通过结论（§7.5、§10.8） |
| B9 | 存在未过门禁的临时插入变更 | 不得给出通过结论 |
| B10 | 门禁未通过仍要求发布 | 拒绝执行发布；按升级规则升级（§4 发布专员红线） |
| B11 | 模板或材料文件缺失 | 阻断，先补齐 |

**紧急豁免**：仅当项目总管给出**书面**批准并载明有效期时，方可对 B3-B6 中的缺项做有条件豁免；豁免记录必须写入发布单 §7，缺少任一要素即视为无豁免（§7.5、§5.3 发布门禁豁免规则）。

## 7. 升级规则

1. 缺项 **2 小时**未补齐 → 升级项目总管（§7.4.1）。
2. 门禁结论争议 → 项目总管组织发布评审会仲裁，但**不得无依据强行放行**（§7.4.2、§7.5）。
3. 紧急发布 → 项目总管书面批准 + 有效期，并留痕（§7.5）；发布后补齐全量记录。
4. 发布后验证失败 → 立即按回滚方案回滚并升级项目总管（§4 发布专员完成标准）。
5. 用户对业务结果不认可 → 走用户验收门禁与复盘，不在本 skill 内改判技术质量结论（§3.5、§3.4）。
6. 同一版本反复门禁不通过（≥3 次）→ 升级复盘（§7.4.3）。

## 9. 示例

**输入**

> 发布单 REL-20261022-01，目标版本 v1.4。材料：测试报告 TR-20261022-01（质量门禁结论：通过，阻断缺陷 0）；文档检查单 DC-20261022-01（文档门禁结论：通过）；回滚方案缺失；审批记录已签。发布专员申请放行。

**输出（摘要）**

- 逐项检查：G1 通过、G2 通过、G3 通过、G4 通过、G5 通过、G6 **不通过**（无回滚方案）、G7 通过、G8 不适用、G9 通过。
- 结论：**阻断**（触发 B5）。阻断清单：缺回滚方案 → 责任角色 软件发布专员 → 要求动作：补齐触发条件/步骤/责任人/数据处理/验证方式/预计耗时 → 期限：发布窗口前。
- 升级：通知项目总管；若因生产事故必须先上线，须由项目总管给出**书面**批准与有效期，写入发布单 §7 后方可转为有条件通过，且记录未完成项与风险处置。

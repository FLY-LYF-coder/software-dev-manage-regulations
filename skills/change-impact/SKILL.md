# change-impact（变更影响分析与变更单）

> RACI：变更管理 A = 项目总管，R = 项目论证专员（§6）。
> 确认权：项目总管组织影响分析后确认，用户做业务取舍确认（§3.3.5）。本 skill 只产出分析与选项，不代替这两方拍板。

## 1. 触发条件

1. 用户提出范围变更申请（§3.3.5）。
2. 接口契约需要变更（§7.5）。
3. 已发任务卡的依赖失效，需重排范围或排期。
4. 紧急插单、紧急发布需要评估对在办工作与在发版本的影响（§7.2、§7.5）。
5. 门禁豁免申请需要评估风险与剩余影响（§7.5）。
6. 需求包定稿后发现与既有范围不一致，需要归口为变更而非直接改包。

不适用：新需求的需求包澄清与论证（`requirement-package`）；变更确认后的任务卡改版（`task-card`）。

## 2. 输入

| 输入 | 说明 | 缺失时处理 |
|---|---|---|
| 变更申请 | 内容、提出人、来源、时间 | 阻断（见 §6） |
| 变更原因与目标 | 为什么改、改成什么 | 阻断 |
| 基线 | 变更前的需求包、任务卡、契约、排期、WIP | 阻断，无法评估即无法决策 |
| 受影响对象线索 | 模块、依赖方、在发版本、时间窗 | 可由论证专员枚举后回确认 |
| 模板 | `docs/team-management/templates/change-order.md` | 阻断 |

## 3. 前置检查

> **D0 规范与模板定位（所有 skill 通用，先于其余检查）**：本 skill 引用的规范与模板均为仓库相对路径 `docs/team-management/...`。定位顺序：① 环境变量 `TEAM_MGMT_ROOT`；② 以本 SKILL.md 所在目录为基准逐级向上查找 `docs/team-management/` 目录；③ 当前工作目录下的 `docs/team-management/`。三者均未命中 → 按 §6 阻断，并提示设置 `TEAM_MGMT_ROOT` 或以本仓库为工作目录。定位到的根目录记为 `MGMT_ROOT`，下文出现的 `docs/team-management/...` 一律相对 `MGMT_ROOT` 解析。

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| P1 | 来源与提出人明确 | 用户侧变更必须已经项目总管登记（§3.2.2、§3.3.5） |
| P2 | 原因与目标已陈述 | 可区分"为什么改"与"想改成什么" |
| P3 | 变更类型已分类 | 范围 / 接口 / 优先级 / 紧急插单 / 紧急发布 / 门禁豁免 |
| P4 | 基线可锁定 | 能指出被改动的具体版本或任务卡编号 |
| P5 | 影响面可枚举 | 受影响对象能逐个列出，不靠"应该没影响" |
| P6 | 时间窗明确 | 期望完成时间与不可动的外部节点（如发版日、月末）已知 |
| P7 | WIP 现状可查 | 在办任务数与里程碑占用可统计（§7.2） |
| P8 | 模板可用 | 模板文件存在 |

P1、P4、P5 任一不通过 → 按 §6 阻断。

## 4. 执行步骤

1. **登记变更单**：填基本信息与变更类型，锁定基线（需求包、任务卡、契约、排期、WIP 的变更前状态）。
2. **枚举影响面**：逐项列出受影响的 任务卡、接口契约、模块、测试用例、文档、发布单/发布计划、里程碑，以及受影响角色。
3. **评估维度**：工作量、依赖链、质量风险（需重跑的测试与回归范围）、文档影响、发布影响、WIP 与排期影响。
4. **出影响矩阵**：变更项 × 影响对象 × 影响程度（高/中/低）× 影响说明 × 处置建议（§4 模板 §4）。
5. **给选项与代价**：至少覆盖 A 接受 / B 延后 / C 拆小 / D 拒绝；**每个选项必须写明代价与风险**，禁止只写"建议接受"。
6. **标记不可逆项**：如已发版本已含被改内容、已对外承诺时间，单独标出并交总管决策。
7. **确认请求**：把影响矩阵与选项交项目总管确认；涉及业务取舍的同时请用户确认（§3.3.5）。
8. **落账改版**：确认后更新需求包/任务卡/接口契约，版本递增，受影响任务卡交 `task-card` 改版；需要重跑的门禁与测试范围在变更单 §8 列明。
9. **记录变更与豁免**：写明原因、批准人、有效期（§7.5、§8.7）。属门禁豁免类的，豁免记录必须含项目总管**书面**批准与有效期，缺一无效。
10. **留痕与度量**：归档变更单，并把影响计入需求变更率等度量（§7.6）。

## 5. 输出

| 输出 | 路径 / 位置 | 说明 |
|---|---|---|
| 变更单 | `docs/team-management/templates/change-order.md`，实际文件 `change-order-<CHG-ID>.md` | 含基线快照、影响矩阵、选项与代价、确认记录 |
| 影响矩阵 | 变更单 §4 | 变更项 × 影响对象 × 影响程度 × 处置建议 |
| 选项与代价说明 | 变更单 §5 | A/B/C/D 各自代价与风险 |
| 确认请求 | 变更单 §6 | 项目总管确认 + 用户业务取舍确认栏 |
| 豁免记录 | 变更单 §7 | 原因、项目总管书面批准人、有效期、剩余风险 |
| 变更后动作清单 | 变更单 §8 | 需改版的需求包/任务卡/契约、需重跑的门禁与测试、需更新的文档、需重排的排期与被挤占任务 |

下游消费方：项目总管（确认）、用户（业务取舍）、`task-card`（改版）。

## 6. 拒绝/阻断条件

| 编号 | 条件 | 处置 |
|---|---|---|
| X1 | 变更无来源或未经项目总管登记 | 阻断，先走 `user-request-intake`（§3.2.2） |
| X2 | 基线不可锁定 | 阻断，无法定位被改动对象 |
| X3 | 影响面无法枚举 | **不出影响结论**，先补枚举；无法评估即无法决策 |
| X4 | 变更试图免于任务卡与门禁（"直接改就行"） | 拒绝，按变更流程走（§8.1、§10） |
| X5 | 变更仅口头或群消息提出且无留痕 | 阻断，先补书面变更单（§8.7） |
| X6 | 门禁豁免类变更缺项目总管书面批准或有效期 | 不得成立，豁免无效（§7.5、§10.8） |
| X7 | 试图绕过用户验收或发布门禁 | 拒绝（§3.4、§10.3） |
| X8 | 论证专员自行批准影响重大的变更 | 拒绝，确认权在项目总管与用户（§6、§3.3.5） |
| X9 | 变更实为新需求 | 转 `requirement-package`，不按变更处理 |
| X10 | 模板文件缺失 | 阻断，先补模板 |

## 7. 升级规则

1. 影响面跨 **3 个及以上角色** → 升级项目总管组织专项评审（§7.4.2）。
2. 变更与在发版本冲突 → 立即升级项目总管决定顺延或撤回（§7.4.1）。
3. 变更导致里程碑延期或触碰对外承诺 → 立即升级项目总管，并同步用户。
4. 同一模块连续变更 **≥3 次** → 升级复盘，检查原始需求、契约或方案问题（§7.4.3）。
5. 紧急变更无法在现有 WIP 内安排 → 升级项目总管做插单与被挤占任务决定（§7.2）。
6. 变更门禁争议 → 由项目总管组织评审，但不得无依据强行放行（§7.4.2、§7.5）。

## 9. 示例

**输入**

> 用户在需求评审会上提出：CSV 导出还要支持按区域筛选。
> 基线：REQ-20261020-01 已定稿；TASK-20261021-01（后端开发中）在办；IC-20261012-01 已会签；目标发版 v1.4（10 月 28 日发版窗口）。

**输出（摘要）**

- 变更类型：范围变更；基线锁定：REQ-20261020-01 v1 / TASK-20261021-01 开发中 / IC-20261012-01 v1 / v1.4 发版窗口。
- 影响矩阵：接口契约 IC-20261012-01（需加 region 参数，中）→ 需重新会签；TASK-20261021-01 工作量 +1 人日（中）→ 需改版；测试用例新增 2 条回归（中）；文档：接口文档 + 用户说明（中）；发布计划：v1.4 内容增加、窗口不变（低）→ 无需顺延。
- 选项：A 接受（代价：TASK 延期 1 人日，v1.4 范围变大）/ B 延后到 v1.5（代价：财务月末需求不满足）/ C 拆小，v1.4 先交付固定全量导出 + 筛选放 v1.5（代价：多一次需求沟通）/ D 拒绝（代价：不满足业务价值）。
- 确认请求：交项目总管；因涉及业务取舍，同时请用户确认。
- 结论未落账前，不改需求包、不改任务卡、不改契约；待确认后由 `task-card` 改版 TASK-20261021-01，并登记 IC 重新会签与新增回归范围。

# weekly-review（周计划会与月度/迭代复盘）

> 复盘报告是项目总管的主要输出（§4）。度量用于改进，不用于简单排名（§7.6）。
> 本 skill 只组织改进与排期输入，不在此宣布门禁通过或发布（§8.5、§10.9）。

## 1. 触发条件

1. 每周计划/评审会（§7.3.2）：排优先级、评审需求与方案、确认发布。
2. 月度复盘（§7.3.4）：看度量、找根因、定改进项与 Owner。
3. 迭代复盘：迭代收尾时复盘目标达成与流程问题。
4. 规范升版前梳理改进项（§11）。
5. 度量异常专项复盘（如阻塞平均时长、返工率、缺陷逃逸率异常升高）。

不适用：任务卡生成（`task-card`）；需求包论证（`requirement-package`）；门禁结论出具（`release-gate-check`）。

## 2. 输入

| 输入 | 说明 | 缺失时处理 |
|---|---|---|
| 任务卡索引与状态 | 各任务状态、Owner、优先级 | 阻断（见 §6） |
| 阻塞清单 | 阻塞项、Owner、已阻塞时长、升级记录 | 可从任务卡与升级记录汇总 |
| 缺陷与返工数据 | 缺陷单、重交与返工记录 | 缺则对应度量不出数 |
| 发布数据 | 发布单、发布结果、回滚记录 | 用于发布成功率与回滚率 |
| 升级与豁免记录 | 原因、批准人、有效期（§7.5） | 缺则 §9 不完整 |
| 改进项候选 | 上期未完成改进项 | 必查（闭环检查） |
| 模板 | `docs/team-management/templates/weekly-review.md` | 阻断 |

## 4. 执行步骤

1. **定范围**：明确本次会议类型、周期、复盘目标与参与角色。
2. **拉数据**：汇总任务卡状态、阻塞、缺陷、返工、发布与回滚记录。
3. **算度量**：按 §7.6 九项指标取数并与上期对比，**同时写明口径**；取不到数的指标标注"本期不可取"并说明原因，不估算。
4. **周会部分（§7.3.2）**：确认优先级 → 评审需求/方案（被退回项写明补齐责任与期限）→ 确认发布（只写发布单编号与门禁状态，不宣布通过）。
5. **定位异常**：对每个异常度量定位到具体任务卡或流程环节，不停留在"沟通不畅""需求变更多"这类泛化结论。
6. **写根因**：对定位结果做根因分析，区分需求侧、契约侧、方案侧、协作侧、执行侧。
7. **定改进项**：每项含 问题 → 根因 → 改进动作 → 唯一 Owner → 期限 → 验证方式 → 关联任务卡；无 Owner 或无期限的不写入改进项清单。
8. **回填改进项**：已成立的改进项转 `task-card` 生成任务卡；未成立的下期先验证再立项。
9. **升级与豁免回顾**：核对本周期所有升级记录与豁免记录，确认均有原因、批准人、有效期，缺失即列为待补项。
10. **归档留痕**：报告与改进项归档，与需求包/任务卡/缺陷单/变更单/交接单建立关联。
11. **闭环检查**：下期开始前确认上期改进项是否全部落任务卡，未落地的写明原因。

## 5. 输出

| 输出 | 路径 / 位置 | 说明 |
|---|---|---|
| 周报 / 复盘报告 | `docs/team-management/templates/weekly-review.md`，实际文件 `weekly-review-<YYYYWW 或 YYYY-MM>-<迭代>.md` | 含任务状态汇总、阻塞清单、度量对比、根因分析、改进项、待排期清单、会议决议 |
| 改进项清单 | 报告 §6 | 每项含问题、根因、动作、唯一 Owner、期限、验证方式、关联任务卡 |
| 度量对比表 | 报告 §4 | 本期 vs 上期 + 口径说明；不可取的指标标注原因 |
| 根因分析记录 | 报告 §5 | 异常度量 → 关联任务卡/流程环节 → 根因结论 → 证据 |
| 待排期清单 | 报告 §7 | 转 `task-card` 的需求与事项 |
| 升级与豁免回顾 | 报告 §9 | 原因、批准人、有效期、当前状态 |

下游消费方：项目总管（排期与承诺）、`task-card`（改进项立项）、团队各角色（改进项执行）。

## 6. 拒绝/阻断条件

| 编号 | 条件 | 处置 |
|---|---|---|
| W1 | 任务卡状态或基础数据缺失 | **不出结论**，先补数据（度量失真会误导排期） |
| W2 | 改进项无唯一 Owner 或无期限 | 不得写入改进项清单，不进入下期排期 |
| W3 | 度量口径未声明 | 不出度量对比（口径不可比的数据无意义） |
| W4 | 复盘被用作排名或追责 | 改写为改进导向；指标用于改进，不用于简单排名（§7.6） |
| W5 | 未完成事项无归属 | 阻断，先定 Owner 再出报告 |
| W6 | 试图在复盘中宣布门禁通过或发布 | 拒绝，门禁结论由守门禁角色出具（§2.3、§8.5） |
| W7 | 试图在复盘中直接改任务卡优先级或派活 | 拒绝，改进项走 `task-card`（§8.5、§3.4.1） |
| W8 | 豁免记录缺原因/批准人/有效期 | 列为待补项，不计入合规统计 |
| W9 | 模板文件缺失 | 阻断，先补模板 |

## 7. 升级规则

1. 阻塞平均时长超阈值或阻塞连续两期未收敛 → 升级项目总管做专项处理（§7.4.1）。
2. 连续两期出现同一根因 → 升级为流程或制度修改提案，进入 §11 的 changelog 流程。
3. 改进项超期未完成 → 升级项目总管重排优先级与 Owner（§7.2）。
4. 跨角色根因争议 → 项目总管仲裁（§7.4.2）。
5. 根因指向质量门禁或发布门禁执行方式 → 由项目总管组织专项评审，**不得无依据强行放行**（§7.4.2、§7.5）。
6. 发现未登记的绕过流程行为 → 升级项目总管处理（§10.10、§3.2.5）。

## 9. 示例

**输入**

> 月度复盘：本周数据 —— 任务 18 个（完成 11、阻塞 3、逾期 2、待验收 2）；缺陷逃逸率从上期 4% 升至 11%；返工率 9%；阻塞平均时长 6.5 小时（阈值 2 小时）；本周期有 2 次紧急发布豁免记录。

**输出（摘要）**

- 阻塞清单：3 项阻塞，均已挂 Owner；平均 6.5 小时 → 超阈值，触发升级规则 1。
- 度量对比：缺陷逃逸率 4% → 11%（口径：发布后发现的缺陷 / 发布缺陷总数，本期取自 2 次发布单）；返工率 9%；阻塞平均时长 6.5 小时（超 2 小时阈值）。其余指标本期不可取并写明原因。
- 根因：逃逸率上升定位到具体任务卡 TASK-20261021-01 —— 该任务在 2 次紧急发布中均未纳入完整回归范围（测试结论显示仅跑了主路径），根因归为**紧急发布流程未强制回归范围**，而非"测试同学疏忽"。
- 改进项：紧急发布流程增加"回归范围必填项"，Owner = 项目总管（流程所有者），期限 2 周，验证方式 = 下次紧急发布时发布单 §4 回归范围栏有值且经质量检测员确认；关联任务卡待生成。
- 豁免回顾：2 次紧急发布豁免均有原因、批准人、有效期 → 合规；无待补项。
- 输出 `weekly-review-2026-10-M10.md`，改进项转 `task-card` 立项。

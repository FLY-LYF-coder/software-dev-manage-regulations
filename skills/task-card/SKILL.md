# task-card（任务卡生成与改版）

## 1. 触发条件

1. 需求包通过需求门禁与评审后，需要把需求落成可执行任务卡（§5.1 步骤 3-4）。
2. 已有任务卡因范围、依赖、优先级或 Owner 变化需要改版（§7.5）。
3. 紧急插单需要新建或改版任务卡（§7.2、§8.8）。
4. 任务回退到"待排期 / 待开发"状态需要重新定范围与验收标准。

不适用：需求受理与登记（用 `user-request-intake`）；发布门禁检查（用 `release-gate-check`）。

## 2. 输入

| 输入 | 说明 | 缺失时处理 |
|---|---|---|
| 需求包 | 目标、范围、非范围、验收标准、优先级建议、风险 | 阻断（见 §6） |
| 评审结论 | 需求门禁结论、里程碑与迭代归属 | 阻断 |
| Owner 候选与在办清单 | 用于唯一 Owner 指派与 WIP 校验 | 阻断 |
| 接口契约 | 涉及联调的任务必须已会签 | 阻断联调部分（§10.3） |
| 测试/文档/发布要求 | 由需求包与发布计划推导 | 可由项目总管据规范补齐后留痕 |
| 模板 | `docs/team-management/templates/task-card.md` | 阻断 |

## 3. 前置检查

> **D0 规范与模板定位（所有 skill 通用，先于其余检查）**：本 skill 引用的规范与模板均为仓库相对路径 `docs/team-management/...`。定位顺序：① 环境变量 `TEAM_MGMT_ROOT`；② 以本 SKILL.md 所在目录为基准逐级向上查找 `docs/team-management/` 目录；③ 当前工作目录下的 `docs/team-management/`。三者均未命中 → 按 §6 阻断，并提示设置 `TEAM_MGMT_ROOT` 或以本仓库为工作目录。定位到的根目录记为 `MGMT_ROOT`，下文出现的 `docs/team-management/...` 一律相对 `MGMT_ROOT` 解析。

逐项校验，**全部通过**才允许产出可执行任务卡：

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| P1 | 验收标准 | 存在且逐条可判定（可观察、可测试），并可回指需求包 AC 编号（§10.1） |
| P2 | 唯一 Owner | 恰好一个自然人/角色，不得空缺或并列（§2.2、§10.2） |
| P3 | 优先级 | 已定级并有理由（§4 项目总管红线：不在无优先级时派活） |
| P4 | 范围与非范围 | 范围内外清晰，附禁止事项（§8.1） |
| P5 | 依赖 | 上游依赖、责任角色、状态明确；联调类任务须有已会签契约（§10.3），契约状态取自 `interface-contract.md`（须为"已会签"） |
| P6 | 测试要求 | 自测项与送测条件明确（§10.4），自测清单按 `dev-self-test.md` 落实 |
| P7 | 文档要求 | 交付文档清单与交接时点明确 |
| P8 | 发布要求 | 目标版本与是否走发布门禁明确 |
| P9 | WIP | Owner 在办任务 ≤ 2；插单须写明被挤占任务及影响（§7.2） |
| P10 | 状态 | 取值符合 §5.2 状态流；阻塞与变更单独标记 |

P1-P3、P9 任一不通过 → 按 §6 拒绝生成可执行任务卡。

## 4. 执行步骤

1. **读取需求包**：抽取目标、范围、非范围、验收标准、风险，不自行新增需求（§8.1）。
2. **定 Owner 与协作人**：据能力与负载指定唯一 Owner；协作角色写明协作内容（§6 RACI：排期与任务分配 A/R 为项目总管）。
3. **定优先级与时间**：设定优先级、截止时间与所属里程碑，登记迭代总 WIP。
4. **写范围与非范围**：显式写出本次不做的事与禁止事项，防止执行方扩展。
5. **写验收标准**：把需求包 AC 转为可判定条目，逐条标注验证方式与对应 AC 编号。
6. **写依赖**：上游依赖方与状态；联调类任务附接口契约编号与会签状态，未会签约一票否决联调安排（§10.3）。
7. **写测试要求**：自测项、送测条件、回归范围、是否需要性能/安全/兼容性测试、缺陷分级约定。
8. **写文档要求**：交付文档清单、责任角色、交接时点与版本要求。
9. **写发布要求**：目标版本、发布门禁前置项、回滚责任角色。
10. **写风险与上下文包**：附需求包、契约、验收标准、文档链接与禁止事项（§8.2 最小充分）。
11. **WIP 校验与插单说明**：统计各 Owner 在办数；超限时或列出被挤占任务与影响，或拒绝生成可执行任务卡。
12. **输出与自检**：按模板落盘任务卡，回读逐项复核 P1-P10，任一不满足则退回对应步骤。

## 5. 输出

| 输出 | 路径 | 说明 |
|---|---|---|
| 任务卡 | `docs/team-management/templates/task-card.md` 结构，实际文件 `task-card-<TASK-ID>.md` | 字段齐全，字段清单见模板 |
| 依赖契约状态记录 | 任务卡 §7 | 联调类任务的接口契约编号、版本与会签状态（`interface-contract.md`） |
| 任务卡索引更新 | 任务卡索引（任务 ID / Owner / 优先级 / 状态 / 在办占用） | 供 WIP 统计与交接使用 |
| 阻断清单（被拒时） | 任务卡 §"前置检查"未通过项 + 补齐责任与期限 | 含缺失项、找谁补、期限 |
| 插单说明（插单时） | 任务卡 §12 | 被挤占任务、影响、批准人 |

下游消费方：前端/后端开发工程师、质量检测员、文档维护员（均以任务卡为唯一工作依据，§8.1）。

## 6. 拒绝/阻断条件

| 编号 | 条件 | 处置 |
|---|---|---|
| R1 | 无验收标准或验收标准不可判定 | **拒绝生成可执行任务卡**，退回项目论证专员补齐（§10.1、§5.3 需求门禁） |
| R2 | 无唯一 Owner，或写了多个 Owner | 拒绝，重新指派（§10.2） |
| R3 | 无优先级 | 拒绝（§4 项目总管红线） |
| R4 | WIP 超限且未说明被挤占任务 | 拒绝生成可执行任务卡，先做插单说明或调整排期（§7.2） |
| R5 | 联调类任务缺已会签接口契约 | 阻断联调安排，不生成可执行任务卡（§10.3） |
| R6 | 依赖缺失且无替代方案 | 阻断相关范围，并在阻断清单中标明依赖方与期限 |
| R7 | 任务卡试图引入规范外的流程或改写门禁 | 拒绝并升级项目总管（§7.5、§8.5） |
| R8 | 模板文件缺失 | 阻断，先补模板 |

拒绝时必须输出阻断清单：缺什么 → 依据章节 → 找谁补 → 期限 → 升级对象。

## 7. 升级规则

1. 验收标准或范围争议 → 项目总管仲裁（§7.4.2）。
2. Owner 资源冲突 / 能力不匹配 → 项目总管调整排期或改派。
3. 依赖方 **2 小时**未响应 → 升级项目总管（§7.4.1、§8.8）。
4. 同一任务返工 **≥3 次** → 升级复盘，检查需求、契约或方案（§7.4.3）。
5. 范围变更影响已发任务卡 → 走变更影响分析后改版任务卡，并记录原因、批准人、有效期（§7.5）。
6. 紧急插单与既有任务冲突 → 项目总管决定插单顺序与被挤占任务（§7.2）。

## 9. 示例

**输入**

> 需求包 REQ-20261018-02（后台 CSV 导出）：目标为财务按月导出明细；验收标准 AC-1 导出字段与模板一致、AC-2 10 万行 30 秒内完成；优先级建议 P1。
> Owner 候选：后端开发工程师 B（在办 1 个）；前端 A（在办 2 个）。

**输出（摘要）**

- 生成 `task-card-TASK-20261018-01.md`，Owner = 后端开发工程师 B（唯一），优先级 P1，状态"待开发"。
- 依赖：接口契约 IC-20261018-01（前端 ↔ 后端），前端 A 因在办 2 个暂不可派联调 → 依赖状态"待会签"，P5 通过但 P9 需在评审会说明。
- 测试要求：自测 2 项；送测条件含自测通过；性能测试按 AC-2（10 万行 30 秒）。
- 文档要求：接口文档初稿由后端出，联调完成后交文档维护员。
- 发布要求：目标版本 v1.4，走发布门禁，回滚责任角色 软件发布专员。
- 若此时再插入一个 P0 事故插单：B 的在办将达 3 > 上限 2 → 触发 R4，必须先写明被挤占任务（TASK-20261018-01）与影响，否则拒绝生成可执行任务卡。
